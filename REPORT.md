# Отчёт: детекция и подавление посторонней речи в двухканальной телефонной записи

## 1) Что решали

На входе стерео WAV 8 кГц: канал `A` и канал `B`. Для каждого канала нужно независимо по времени отмечать:
- `own` — говорит владелец канала;
- `leak` — речь собеседника просочилась с другого канала (эхо/наводка);
- `third` — локальный третий говорящий;
- `silence` — тишина/шум (в выход JSON не пишется).

Метки `own`, `leak`, `third` независимы и могут пересекаться (double talk).

Дополнительно: удалить `leak` из каждой дорожки (`clean.py`) и показать, что очищенный сигнал ближе к чистой речи владельца по speaker embedding.

---

## 2) Принятые допущения и генератор данных

Реальных размеченных записей не было, поэтому качество модели зависит от качества синтеза. Генератор сделан как часть решения (`src/synthesizer.py`).

Что моделируется:
- телефонный тракт `T`: полоса 300–3400 Гц, A-law, packet loss 20 мс, шум;
- просачивание `leak`: задержка 20–300 мс, затухание 6–40 дБ, нелинейность динамика (`tanh`), отдельный RIR;
- `path_drift`: плавное изменение задержки внутри звонка;
- третий говорящий: отдельная дорожка с более «дальним» RIR и ослаблением.

Данные:
- речь: `data/russian_speech`;
- train/test разделены по дикторам (в коде train: `ru_spk_1..4`, test: `ru_spk_5..7`);
- RIR/шумы: OpenSLR 28 (если недоступно — fallback на синтетический RIR/шум).

Сценарии синтеза для обучения и оценки:
`normal`, `double_talk`, `high_leak_lt_10db`, `path_drift`, `third_speaker`.

Почему так: задача проверяется на другом генераторе, поэтому важно учить не «паттерны одного датасета», а устойчивые физические признаки канала и утечки.

## 3) Метод

### 3.1 Baseline (обязательный по ТЗ)

`src/baseline.py`: правило +6 дБ.
- если энергия канала выше второй дорожки минимум на 6 дБ → `own`;
- иначе → `leak`;
- `third` baseline не предсказывает.

Это контрольная точка для сравнения.

### 3.2 Детектор (`detect.py`, `src/detector.py`)

Подход: **быстрые физические признаки + лёгкая контекстная нейросеть**.

#### Признаки (10 мс шаг, 36 признаков на кадр)
Из `src/features.py`:
- энергия и ILD;
- GCC-PHAT пик и оценка задержки в окне 20–300 мс;
- NLMS residual ratio (насколько канал объясняется адаптивной фильтрацией от второго канала);
- спектральные признаки (центроид, flatness, hi/low);
- 12 log-mel локального канала + 12 log-mel второго;
- признаки speaker anchor (насколько кадр похож на «типичную» речь владельца этого канала).

#### Модель
`_DetectorNet`: 1D TCN (Conv1d + 4 residual dilated блока с дилатациями 1/2/4/8).
Выход: 3 независимых вероятности (`own`, `leak`, `third`) на кадр.

Почему это решение:
- соблюдает ограничение по скорости на CPU;
- контекст ~600 мс снижает дребезг по границам;
- независимые выходы корректно покрывают double talk.

#### Постобработка
- пороги: `own=0.50`, `leak=0.50`, `third=0.38`;
- медианная фильтрация вероятностей;
- минимальная длина сегментов (строже для `third`).

### 3.3 Очистка (`clean.py`, `src/cleaner.py`)

Цель: убрать `leak`, не испортив `own`.

Схема:
1. STFT для обоих каналов.
2. Оценка задержки по огибающим и выравнивание второго канала.
3. Оценка спектра утечки `leak_estimate`.
4. Маска подавления:
   - нейросетевой 32-band IRM (`_CleanerNet`),
   - аналитическая Wiener-подобная часть,
   - гибрид в double talk.
5. Режимы:
   - pure own: почти не трогаем;
   - pure leak: агрессивное подавление + comfort noise;
   - double talk: селективное подавление с защитой владельца.

Почему так: чисто аналитический фильтр даёт артефакты на сложных участках, чисто нейросетевой — хуже контролируется в крайних режимах. Гибрид стабильнее.

## 4) Обучение

### Детектор
`scripts/train_detector.py`:
- синтезируются диалоги по 5 сценариям;
- берутся признаки на канал;
- таргет — покадровые multi-label маски;
- loss: `BCEWithLogitsLoss` (с повышенным весом для `leak` и `third`);
- оптимизатор `AdamW`, scheduler `CosineAnnealingLR`.

### Cleaner
`scripts/train_cleaner.py`:
- признаки строятся из STFT + вероятностей детектора;
- таргет — IRM к `target_audio` (сигнал без утечки из генератора);
- loss: комбинация MSE по маске и спектрального члена;
- повышенный вес кадров `double_talk`.

## 5) Оценка и сравнение с baseline

Оценка делалась скриптом `evaluate.py`:
- F1 по 10 мс кадрам (`own`, `leak`, `third`), collar 50 мс;
- breakdown по сложным сценариям;
- speaker purity (ECAPA embedding);
- leak attenuation (дБ);
- RTF на 1 CPU (`OMP_NUM_THREADS=1`).

## 6) Где решение ошибается и почему

1. **Плотный double talk**: при сильном перекрытии гармоник владельца и утечки в узкой полосе 8 кГц их трудно разделить без потерь речи владельца.
2. **Границы сегментов**: контекстная модель даёт инерцию на резких концах фраз.
3. **Тихий third на фоне громкого own/leak**: энергетически и спектрально класс может маскироваться.
4. **Доменные сдвиги**: редкие реальные нелинейности тракта, не попавшие в генератор, дают деградацию качества.

## 7) Что делать дальше (ещё неделя)

1. Добавить complex-mask/phase-aware вариант cleaner для более качественной работы в double talk.
2. Усилить обучение на hard mining (случаи с низким SNR third и очень малым затуханием leak).
3. Калибровать пороги детектора по сценариям и добавить uncertainty-aware постобработку.
4. Расширить реалистичность генератора (больше профилей нелинейности, jitter, variation packet loss).
